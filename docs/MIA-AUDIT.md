# What the MiaAI-Lab vLLM kit does that we could use

This audit covers [MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks)
(main @ `943912c`, 2026-09-27: README, docs/, overlay/, PRs merged in the last ~4 weeks, and open PRs that report
measurements) and its sibling [Reederey87/glm53-flash-exl3-2x-dgx-spark](https://github.com/Reederey87/glm53-flash-exl3-2x-dgx-spark)
(@ `a908a17`, the upstream of our production vLLM kit; mostly its `local/` ops scripts). For each item, the question
is whether it carries over to TensorFold.

TensorFold is a different engine. It has no vLLM scheduler, no paged KV pool, no APC, and no `gpu_memory_utilization`.
Instead it has fixed capacity-sized buffers (docs/MEMORY-1M.md), a session store (0110), and one request at a
time unless `GLM53_TF_BATCH` is set. Many of Mia's wins are fixes to vLLM itself, so they don't apply here.

"Receipt" means a number quoted from their PR body or README. We did not re-measure any of them. "Gain for us" is
our estimate. None of the items below changes the model's output unless the item says so. FP8 prefill was already
rejected here, so the FP8 items are listed only as not applicable.

### What `scripts/serve.sh` does differently with no new knob set

- `start` refuses when either node runs a CUDA process, as documented. Before, a head PID could read as "free" (the `grep -q` SIGPIPE bug above).
- `start` and `restart` take a lock (`$STATE_DIR/lock`, default `~/.local/state/glm53-tf/lock`), so a second concurrent start exits 1 instead of removing the first one's containers. If the directory isn't writable or `flock` is missing, it goes on without a lock.
- A worker ssh failure while waiting for readiness is retried twice before the start fails. Before, one ssh hiccup failed the start.
- `stop` (and the teardown at the start of `start`) removes both ranks in parallel.
- `status` also prints `/health`.
- New subcommands: `restart`, `preflight`, `canary`, `xid`, `watch`.
- Unchanged: the log format, the docker run flags (no log options and no NCCL extras unless set), the unbounded readiness wait, no canary, no preflight, no memory wait.
- Patch 0140 (fast boot) changed the same file separately: parallel rank start, 1 s polling, the `/prepared` mounts, `GLM53_TF_CALIB=cached`.

## What needs a GPU run before relying on it

- **Canary thresholds.** Run `scripts/serve.sh canary` (or `python3 scripts/canary.py --json`) on a healthy load and
  record tokens/round and decode tok/s on the probes. Keep `CANARY_MIN_TPR` well below the healthy value (1.3 is
  conservative for DFlash2 at k=7 on these prompts). Then set `CANARY_MIN_TPS`. Also check that the three replies
  pass on the real model: greedy, thinking off, abliterated weights.
- **0150 under load.** `/metrics` counters against the per-request `tensorfold` stats; `GLM53_TF_HEALTH=strict`
  with `GLM53_TF_STALL_S=600` through a 1M prefill (the allowance at 200 tok/s is ~83 min) and a long thinking
  reply; a forced engine error (e.g. an OOM-sized request with a batch knob) giving 503 + refusal + a watchdog heal.
- **`reasoning_effort` mapping.** Re-run #279's structured prompt: thinking off vs `reasoning_effort: low`.
- **MemFree gate value.** Read idle MemFree on both nodes after a stop (Reed's idle is 93-97 GiB with the page cache
  full) and pick `MEM_GATE_GIB` a few GiB under it.
- **Xid access.** `serve.sh xid 24h` on the real nodes has to be able to read the kernel log: the head user needs
  the `systemd-journal` or `adm` group, and the worker's ssh user too. Without it journalctl prints nothing and no
  Xid is reported.
- **WARMUP_LENGTHS.** Time the first 16k/32k request after boot with and without it.
